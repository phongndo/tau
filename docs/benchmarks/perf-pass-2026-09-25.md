## Environment and limits

- Host `z`: NixOS, Linux 6.18.48, AMD Ryzen 9 9950X (32 threads), 30 GiB RAM. Commands ran through `nix develop` (Bun 1.4.2, Zig 0.16.0, Node 24.15.0).
- Electron 44.4.5: Chromium 152.0.7977.130, embedded Node 24.21.0, V8 15.2.124.28-electron.0.
- Renderer measurements ran under Xvfb (1920×1080×24). Chromium's GPU process exits there (no GLX), so canvas work is software-rasterized. **No real-display, GPU-composition, or presentation-latency result is claimed.** Timings end at `requestAnimationFrame` callback completion, not at pixels on screen.
- Unrelated workloads shared the host (load average 1–7). Every A/B alternated baseline and candidate in separate Electron processes with identical workloads; startup samples were still too noisy to compare (below).

## Method

`bun run bench:surface` ([`tau-surface-entry.ts`](../../apps/desktop/bench/tau-surface-entry.ts), [`tau-surface-benchmark.ts`](../../apps/desktop/bench/tau-surface-benchmark.ts)) runs the production `TauTerminal`, sequenced writer and packaged Ghostty WASM in a sandboxed renderer. Each pane receives 4 KiB complete frames through a `MessageChannel`, one message per frame, with main-like flow control (≤512 frames, ≤2 MiB unacknowledged). Real Chromium key events arrive every 50 ms; each emitted key queues a one-byte "PTY echo" behind in-flight output. A run fails on a resync, drop, unacknowledged frame, missing end marker or blank canvas; parked panes must show their end marker after reattach.

- Geometry: 1200×720 px (99×40 cells with the fallback font); quad = 2×2 panes of 49×20. `single-plain` 16 MiB of text; `single-ansi` 8 MiB of SGR/256-colour/truecolour lines; `quad-ansi` 4 × 4 MiB; `parked-ansi` 4 × 4 MiB into panes parked like `terminal.ts`, plus one idle visible pane receiving input.
- Metrics: _parse_ = first frame posted → last frame acknowledged; _draw work_ = time inside rAF callbacks; _key→data_ = key event timestamp → `onData`; _echo_ = echo frame posted → acknowledged (parse, not paint); _lag_ = overshoot of a 4 ms timer chain; renderer task/layout time from CDP `Performance.getMetrics`; allocation from CDP sampling heap profiler (16 KiB interval, including collected objects); retained heap from CDP `collectGarbage` + `Runtime.getHeapUsage`.
- The baseline bundle was built from a baseline worktree with the same entry file and selected with `TAU_SURFACE_BENCH_SCRIPT`.

## Packaged app (Xvfb, daemon pinned with `TAUD_PATH` to the unchanged taud)

All passed for the candidate: `bench:taud:budget` 2/2 (baseline 1/2; one launch-smoke timeout), `bench:startup:budget`, `bench:reload:budget`, `bench:app-soak:budget` 2/2 each, and the 8 MiB flood/input smoke (`TAU_ELECTRON_SMOKE_OUTPUT_BYTES=8388608 TAU_ELECTRON_SMOKE_MAX_INPUT_ECHO_MS=500 TAU_ELECTRON_SMOKE_OUTPUT_TIMEOUT_MS=8000 bun run smoke:package`) 2/2 each, with input echo 7.9/7.4 ms (and 11.2 ms in a final-tree rerun) versus 12.4/15.3 ms at similar throughput; these are few samples. Pin `TAUD_PATH` for any A/B: without it, the app resolves `apps/daemon/zig-out/bin/taud` before the packaged binary.

Startup (first pane, WASM fetch → first prompt draw) was inconclusive: host-load outliers up to 10.9 s hit both variants; the four quietest paired samples were 25–47 ms (baseline) and 33–36 ms (candidate). The startup path is unchanged apart from reading the cell layout once per terminal.

## Rejected experiment: amortized daemon excerpt compaction

`appendBoundedExcerpt` rewrites the 1 MiB search excerpt on every PTY read (append, read back, truncate and rewrite) while holding the daemon mutex. Letting it grow to 2 MiB before rewriting the tail cut a 16 MiB full-rate flood's file I/O from ~4.4 GB read / 3.8 GB written (0.3–0.4 MiB/s) to ~48 MB / 75–114 MB, and input-priority echo under a slow-subscriber flood from p50 2.0–2.1 ms to 0.04–0.06 ms. It was **not retained**: with the daemon pinned, the faster daemon outran Electron main on tiny (≈57–64 byte) frames, was dropped as a slow subscriber (`SlowClientBackpressure`), failed `bench:taud:budget` 3/3, and one run crashed taud with SIGSEGV on a worker thread (stripped binary; not diagnosed). The baseline daemon passed 3/3. The excerpt write amplification is real, but fixing it first requires per-frame coalescing or bounded buffering between taud, main and the renderer so that a faster producer does not turn into drops or crashes.

## Validation and known gaps

Commands: `bun run check`, `bun run build`, `bun run zig:leak-check`, `bun run test:surface` (39 checks), `bun run smoke:package`, `bun run --filter @tau/desktop test:shell-lifecycle`, `bench:latency:budget`, `bench:input-priority:budget`, `bench:attach:budget`, `bench:soak:budget`, `bench:ipc:budget`, and the packaged budgets above. A baseline/candidate differential run compared 2,400 rendered frames (1,577,614 cells: SGR, 256/truecolour, erase backgrounds, graphemes, wide cells, selection, resize, scrollback, light palette) with identical output.

Not established: hardware GPU/real-display presentation, frame pacing on a physical display, macOS behaviour, platform IME, font-dependent glyph advances other than the Xvfb fallback font, and whole-app CPU/energy. `bench:terminal`/`bench:renderer` measure an xterm.js harness and were not used as evidence. `bun run --filter @tau/desktop test:taud-lifecycle` ("restarts an owned real daemon") fails identically at the baseline.
